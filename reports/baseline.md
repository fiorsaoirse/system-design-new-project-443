## Вывод

Основной проблемой является то, что на каждый запрос база данных полностью сканирует все строки таблицы, чтобы сначала отфильтровать всех пользователей, а затем отсортировать записи по полю created_at и взять 20 последних записей. 

Это видно из плана запроса:

```
Parallel Seq Scan on trips  (cost=0.00..64569.63 rows=83 width=104) (actual time=1.691..77.189 rows=66.67 loops=3)
                     Filter: (passenger_id = 1)
                     Rows Removed by Filter: 666650
```

По факту, каждый loop отфильтровал 666650 строк, получив в качестве результата 66.67 подходящих строк.

Сканирование при этом занимает ~77ms из всех ~83ms, которые тратит база данных на запрос.

Эту работу можно оптимизировать, добавив в базу данных составной индекс:

```
CREATE INDEX trips_passenger_created_at (passenger_id, created_at)
on trips (passenger_id, created_at DESC);
```

При этом, сначала упорядочить индекс нужно по passenger_id, и только затем уже внутри записей одного пассажира по created_at DESC. Это позволит просто взять с начала блока записей одного пользователя 20 записей (по LIMIT), непрерывно.
